Нотатки:
- Telegram: Telethon (MTProto, звичайний акаунт), бо бот через Bot API не може написати першим. GramJS теж розглядав, але Python зручніший для голосу (faster-whisper, edge-tts) і валідації (Pydantic).
- LLM: OpenAI gpt-5.4-mini. Починав з безкоштовного Gemini, але отримував 404/504 і малі ліміти. Розмова коштує центи; Gemini і Groq лишились як запасні провайдери.
- LLM щоразу повертає JSON (understood, decision, action), який перевіряє Pydantic; з нього агент сам пише лог рішень.
- Невідомі дані агент питає в мене як оператора через Saved Messages, нічого не вигадує.
- Критичні правила перевіряє код, а не промпт: фінальний підсумок формується з даних стану, агент не може сам скасувати бронь чи завершити розмову без підсумку.
- Голос: faster-whisper (локально) для розпізнавання, edge-tts з британським голосом для озвучки, ffmpeg для OGG/Opus.
- AI: проєкт зроблений у парі з Claude Code (архітектура, код, тести). Живі тести в Telegram проводив сам із двох акаунтів, аналізував логи, кожну знайдену ваду закривав тестом.
Повна історія того, що ламалося: docs/NOTES.md у репозиторії.

Що зламалося і в чому не впевнений:
Під час тестів агент кілька разів поводився неправильно: завершував розмову без фінального підсумку, в одній з попередніх спроб повірив менеджеру, що клієнт скасував бронь, і не перевірив це в мене, повторював те саме прохання кілька разів, плутав голос і текст у відповідях. Усе це виправлено перевірками в коді, а не лише в промпті. У фінальній розмові 17:00 було недоступне, агент сам не погоджувався на інший час, і я як оператор вирішив прийняти 17:30; не впевнений, чи очікувалося, що агент наполягатиме на 17:00 довше. Також момент підтвердження броні досі визначає LLM, тож розмите «ok» теоретично може бути прийняте за підтвердження; розпізнавання голосу може помилятися з цифрами й іменами; edge-tts — неофіційний сервіс.
